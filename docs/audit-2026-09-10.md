# Audit — 2026-09-10

## Fixed scanner process and launch lifecycle

- Added `apps/api/src/supervisor/process-launcher.ts` without another dependency. It binds one exact approved artifact identity to an absolute executable/cwd and fixed bounded arguments, disables shell and environment inheritance, and sends only a bounded canonical scanner-input document to stdin.
- Exact plan shape, canonical hostname, current scanner policy and artifact/profile identity are revalidated before spawn. Spawn plus stdin initialization is capped at five seconds; stdout remains the bounded result IPC channel, stderr is ignored and the handle exposes TERM/KILL.
- Closed the supervisor deadline gap: one deadline and AbortSignal now cover launcher startup, IPC and exit. Cancellation of a pending launch returns promptly; if a valid handle resolves afterward it is killed without entering IPC or signing.
- Split generic process lifecycle handling into `process-lifecycle.ts` to retain the repository's 400-line authored-source limit; execution authorization and result semantics remain in `run-guest.ts`.

## Guest worker process entrypoint

- Added a dedicated API worker entrypoint that composes the existing PostgreSQL/BullMQ runtime, mounted approval and result-key providers, durable telemetry and fixed scanner process adapter. Its configuration permits only bounded absolute paths and a bounded JSON string array of deployment-owned scanner arguments.
- Startup requires the current approved GUEST_SAFE artifact and a fresh 256-bit signing key whose version and bytes match the immutable startup verification keyring. Missing/revoked/malformed approval, unsafe configuration and incomplete or conflicting key rotation deny without exposing provider details.
- The process emits only bounded local ready/telemetry status and stable failure text. It adds no HTTP route, outbound test scan, scanner capability or production deployment claim.

## Minimal first-party GUEST_SAFE scanner

- Added `apps/api/src/guest-scanner` and `guest-scanner-cli.ts` over the existing runtime DNS, full-set destination classifier, pinned HTTPS/same-host redirect flow and scanner IPC encoder. No dependency or public route was added.
- Scanner input independently requires the exact current GUEST_SAFE policy and DNS/TLS/HTTP capability subset. One counter bounds both A/AAAA queries and HTTPS dispatches; built-in or configured forbidden resolution cannot reach transport, inner retries are disabled and raw addresses/headers/body never enter output.
- Added an exact versioned runtime configuration joining DNS settings with a copied list of up to 128 deployment-specific internal CIDRs. Malformed, sparse, duplicate and hostile values fail closed; the same deny-list is used for preflight, retry and redirect resolution.
- Current evidence is deliberately partial: resolution/IPv6 and TLS reachability are observed; HSTS, CSP/frame protection, nosniff, referrer and permissions checks accept only a conservative useful subset. Positive HSTS requires non-zero `max-age`, CSP requires an enforcing directive, duplicate/ambiguous headers and permissive referrer/permissions values stay ATTENTION. This follows RFC 6797 and the W3C CSP, Referrer Policy and Permissions Policy processing models without claiming a complete browser parser.
- RDAP, CT, mail and public-infrastructure coverage is marked unavailable. The scanner has no platform credential, while container/egress isolation remains an external blocker.

## Bounded security.txt observation

- Added a second pinned HTTPS flow for the exact same-host `/.well-known/security.txt` path under the existing GUEST_SAFE HTTP capabilities and shared request counter. Redirects are still limited to the canonical host; cross-host redirects are observed but not followed and cannot pass.
- The dependency-free validator accepts only a conservative unsigned RFC 9116 subset: one `text/plain; charset=utf-8` response, fatal UTF-8, at most 32 KiB/1,000 lines/2,048 bytes per line, at least one supported Contact URI, exactly one future UTC Expires value and a matching Canonical URI when the field is present. BOM, control bytes, malformed or stale fields and ambiguous media types remain ATTENTION.
- Only the stable `SECURITY_TXT` outcome and fixed machine finding fields enter the scanner envelope. Response bodies, contacts, URIs, headers and socket addresses are not projected; presence or absence never grants scan authorization.

## Detached Guest result HTTP boundary

- Added `apps/api/src/guest-http` as an unregistered Fastify plugin over the existing authorized Guest result read port. It accepts only GET on `/v1/public/scans/:scanId`, disables Fastify's implicit HEAD route and rejects every query before reader invocation.
- Success emits only the sanitized view with fixed `no-store`/`no-referrer`. Malformed route/query maps to 400, all token/resource/persistence denials map to one enumeration-resistant 404, and unexpected clock/reader failure maps to a stable redacted 503.
- Six tests prove the mappings, privacy headers, failure containment and that the production `buildApp()` still returns 404 for the route. No Guest route was registered or exposed; deployment controls remain authoritative.

## Detached Guest session bootstrap boundary

- Added an unregistered Fastify plugin for `POST /v1/public/guest-session`. It accepts no query/body, requires one exact configured HTTPS Origin, handles a single raw Cookie header and passes only that value to an injected server-owned bootstrap decision.
- A reused session returns `204` without refreshing its lifetime. Issuance returns only a strictly validated `__Host-outscan_guest_session` Set-Cookie header with the fixed Secure/HttpOnly/SameSite/Path/Max-Age contract; the body is empty and all outcomes use no-store/no-referrer/nosniff.
- Unknown/extra service fields, header injection, unsafe cookie attributes, provider failure and malformed origin configuration fail closed. Production `buildApp()` still returns 404, and the concrete key/revocation-backed bootstrap service remains pending.
