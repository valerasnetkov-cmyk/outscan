# Audit — 2026-09-08

## Transactional Guest retention batches

- Added a dependency-injected PostgreSQL retention worker with exact input/clock validation and bounded scan/window batches. It selects due rows with `FOR UPDATE SKIP LOCKED`, preserving safe concurrent worker execution.
- At or after the fixed 24-hour deadline, the worker reconciles any unreleased session/network active counters and deletes the complete Guest aggregate through existing cascades in one transaction. Expired window counters are pruned independently.
- Privacy deletion proceeds even if quota metadata is missing; the immutable batch report exposes deletion, decrement, stale-window, inconsistency and remaining-work counts plus `alert_required` for the future durable telemetry sink.
- PostgreSQL cases prove exact-deadline deletion, not-yet-due retention, bounded continuation, prior-release idempotency and fail-visible cleanup of damaged active-counter state. No route, scheduler or production telemetry was added.

## Transactional Guest abuse counters

- Added append-only migration `0002_guest_abuse_counters.sql`: server-owned OPEN/PAUSED state, four digest-only window counters, two digest-only active counters and one reservation/release row bound to each GuestScan. The schema contains no raw address, User-Agent or browser-fingerprint field.
- Extended the strict persistence command with a server-derived HMAC network signal. Malformed signals reject before database acquisition and cannot become Guest ownership or result authorization.
- New scan and expired replacement now reserve all six dimensions inside the existing SERIALIZABLE idempotency transaction. Denial rolls back tentative scan/token/counter effects; a valid live replay returns before abuse-state access and consumes no additional quota.
- Concurrent different-key requests for one Guest session converge to one active reservation. Burst/daily usage remains consumed after release, while accepted terminal result and expired replacement decrement active counters exactly once.
- The shared PostgreSQL integration harness now pins one Vitest worker so the intentionally global server-pause row cannot leak across concurrently executing DB files.
- The server pause is read under the persistence transaction. Public 429/Retry-After mapping, trusted-proxy derivation/key rotation, non-success terminal release and retention scheduling/durable metrics remain blocked before Gate B1.

## Atomic Guest terminal result commit

- Added `createPostgresGuestResultCommitter` as the authenticated ResultEnvelope-to-database boundary. Workload, audience, expiry, HMAC, digest and payload size are verified before a database client is acquired.
- The committer rebuilds the canonical GUEST_SAFE payload and sanitized projection from authenticated bytes. Non-canonical payloads and a projection host that differs from the persisted canonical target are rejected without result writes.
- The SERIALIZABLE primary branch locks the current GuestScan/GuestScanAttempt, uses PostgreSQL transaction time and requires RUNNING job/attempt, current attempt/fence and live lease/deadline. Attempt success, job acceptance identity and one immutable GuestResult insert commit atomically.
- The terminal branch acknowledges only the already accepted attempt/fence/digest and performs no payload write. A different digest returns the explicit security-audit signal for the future sink; stale identity and expired execution authority fail closed.
- Serialization/deadlock/result-winner races receive at most three attempts. Unknown database outcomes collapse to `GUEST_PERSISTENCE_UNAVAILABLE`; no PostgreSQL detail is exposed by the repository contract.
