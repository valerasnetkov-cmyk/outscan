# Audit — 2026-09-08

## BullMQ Guest supervisor composition

- Added pinned BullMQ 6.3.4 and ioredis 5.11.1 transport. The closed job payload contains exactly schema version plus a server-created GuestScan ID; deterministic job IDs suppress duplicate enqueue while Redis receives no target, policy, token, attempt, fence or credential.
- The consumer composes the existing PostgreSQL claim/start CAS, a server-derived GUEST_SAFE envelope from the live lease and approved artifact, injected supervisor execution, five-second renewals and authenticated result commit. A lost/unknown renewal aborts the run and prevents commit; PostgreSQL remains the only attempt/fence authority.
- Queue delivery retries are bounded independently from the three-attempt database FSM. Terminal/not-acquirable state is acknowledged, retryable outcomes use closed codes, and unknown job names or expanded payloads fail closed.
- The optional `msgpackr-extract` install script is explicitly denied in the pnpm build allow-list; BullMQ runs with its pure-JS path and an explicit ioredis dependency.

## Trusted ingress and rotation-safe Guest network quota

- Added an exact server-side ingress contract over `socket_remote_address`, optional `X-Forwarded-For` wire value and a maximum-64 trusted-proxy CIDR allow-list. Forwarding metadata is ignored for an untrusted socket peer; behind a trusted peer, at most eight canonical IP literals are walked from right to left to the first untrusted address.
- Ports, IPv6 zones, invalid CIDRs, missing trusted-proxy metadata, unknown fields, excessive hops and chains containing only trusted addresses fail closed. IPv4-mapped IPv6 is normalized before trust and digest decisions.
- Added an active-first network-HMAC keyring projection capped at three distinct 256-bit keys. Missing active versions, duplicate derived identities and malformed/excess keys are rejected; output contains only domain-separated digests.
- The strict persistence input now carries active plus retained digests. Its SERIALIZABLE abuse transaction locks and sums all live alias window/active rows, increments only the active digest and captures that digest in the per-scan reservation for exact later release.
- A normal rotation therefore requires a two-stage deployment and retired-key availability for the 24-hour maximum abuse window plus skew. The database case proves 19 retained-key burst uses plus one active-key use reach the shared limit without rewriting the old counter.

## Transactional Guest cancellation

- Added a queue/route-neutral cancellation persistence boundary that accepts only one exact server-created GuestScan ID after a future upstream trusted decision. It does not expose an HTTP endpoint or establish Guest ownership.
- The SERIALIZABLE transaction locks the job and current attempt. QUEUED jobs cancel directly; LEASED work becomes `SUPERSEDED`, RUNNING work becomes `CANCELLED`, and then the job becomes `CANCELLED` before its abuse-concurrency reservation is released.
- Repeated cancellation returns `ALREADY_CANCELLED` without another decrement. Concurrent callers serialize to one `CANCELLED` plus one idempotent acknowledgement; malformed/unknown/terminal input fails closed.

## PostgreSQL Guest attempt leases

- Added a queue-transport-neutral persistence boundary keyed only by server-created GuestScan ID. A SERIALIZABLE first claim creates `CREATED → LEASED`, sets the current attempt/fence and transitions the job to RUNNING atomically.
- Fixed V1 execution timing is 15-second lease, 45-second hard deadline and three attempts. Start is idempotent for the exact lease; renewal requires the exact current attempt/fence/version and increments the lease version only when expiry advances.
- Duplicate concurrent delivery produces one lease winner. Expired LEASED/RUNNING attempts become SUPERSEDED/TIMED_OUT before a new attempt receives strictly larger attempt/fence values; retry exhaustion or 30-minute access expiry terminalizes the job and releases active abuse quota.
- Added append-only `0003_guest_abuse_expired_release.sql` so access expiry is recorded distinctly from cancellation. Subsequent cancellation and BullMQ slices close the persistence transition/release and supervisor abort composition; public cancellation authorization and production queue metrics remain absent.

## Transactional Guest retention batches

- Added a dependency-injected PostgreSQL retention worker with exact input/clock validation and bounded scan/window batches. It selects due rows with `FOR UPDATE SKIP LOCKED`, preserving safe concurrent worker execution.
- At or after the fixed 24-hour deadline, the worker reconciles any unreleased session/network active counters and deletes the complete Guest aggregate through existing cascades in one transaction. Expired window counters are pruned independently.
- Privacy deletion proceeds even if quota metadata is missing; the immutable batch report exposes deletion, decrement, stale-window, inconsistency and remaining-work counts plus `alert_required` for the future durable telemetry sink.
- PostgreSQL cases prove exact-deadline deletion, not-yet-due retention, bounded continuation, prior-release idempotency and fail-visible cleanup of damaged active-counter state. No route, scheduler or production telemetry was added.

## Transactional Guest abuse counters

- Added append-only migration `0002_guest_abuse_counters.sql`: server-owned OPEN/PAUSED state, four digest-only window counters, two digest-only active counters and one reservation/release row bound to each GuestScan. The schema contains no raw address, User-Agent or browser-fingerprint field.
- Extended the strict persistence command with a server-derived HMAC network signal. Malformed signals reject before database acquisition and cannot become Guest ownership or result authorization.
- New scan and expired replacement now reserve all six dimensions inside the existing SERIALIZABLE idempotency transaction. Denial rolls back tentative scan/token/counter effects; a valid live replay returns before abuse-state access and consumes no additional quota.
- Concurrent different-key requests for one Guest session converge to one active reservation. Burst/daily usage remains consumed after release, while accepted terminal result and expired replacement decrement active counters exactly once.
- The shared PostgreSQL integration harness now pins one Vitest worker so the intentionally global server-pause row cannot leak across concurrently executing DB files.
- The server pause is read under the persistence transaction. Subsequent trusted-ingress/rotation and cancellation slices close proxy derivation, normal key rotation and explicit cancellation release; public 429/Retry-After mapping and retention scheduling/durable metrics remain blocked before Gate B1.

## Atomic Guest terminal result commit

- Added `createPostgresGuestResultCommitter` as the authenticated ResultEnvelope-to-database boundary. Workload, audience, expiry, HMAC, digest and payload size are verified before a database client is acquired.
- The committer rebuilds the canonical GUEST_SAFE payload and sanitized projection from authenticated bytes. Non-canonical payloads and a projection host that differs from the persisted canonical target are rejected without result writes.
- The SERIALIZABLE primary branch locks the current GuestScan/GuestScanAttempt, uses PostgreSQL transaction time and requires RUNNING job/attempt, current attempt/fence and live lease/deadline. Attempt success, job acceptance identity and one immutable GuestResult insert commit atomically.
- The terminal branch acknowledges only the already accepted attempt/fence/digest and performs no payload write. A different digest returns the explicit security-audit signal for the future sink; stale identity and expired execution authority fail closed.
- Serialization/deadlock/result-winner races receive at most three attempts. Unknown database outcomes collapse to `GUEST_PERSISTENCE_UNAVAILABLE`; no PostgreSQL detail is exposed by the repository contract.
